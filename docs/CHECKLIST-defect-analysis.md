# 缺陷结论前置核查清单

> 用途：对第三方代码下缺陷结论、或提出改进方案**之前**跑完这个清单。
> 依据：在 steamworks-rs 分析项目上，12 处自我更正里绝大多数源于跳过本清单的某一步（逐条见文末回溯表）。

---

## A. 下「缺陷存在」结论前

- [ ] **A1. 是否已跑出复现？**
      拿不出复现脚本的，在文档里标「已分析，未复现」，与「已复现」分开列。
      不能把「读代码觉得危险」写成「实测发现问题」。
      **复现脚本自身也可能携带错误假设**——脚本打印的「后果」若来自模拟器自设语义而非
      被测系统真实行为，跑通了也不算证明了那条后果。
      **实例**：UGC builder 复现打印「已写入 Steam 无法回滚」，实为脚本里 Vec 的行为；
      Steam 实际是暂存语义（第 12 处更正）。复现只证明了「panic 会中断链」。

- [ ] **A2. 计数是否可复算？**
      「N 处」必须给出 grep 命令与分类口径。
      **同类错误实例**：把 61（全部 `debug_assert`）说成 null 检查数，实际 23；
      把 83（全部 `CString::new`）与 73（带 unwrap 的）混用而未说明关系。
      一个数字若有两个合理口径，两个都要写，并说明各自含义。
      **写「这个数字没错」这类断言前，重新跑一遍 grep**——数字可能来自已失效的本地改动
      （实例：「37 处」实测 42，历史提交上也无 37，是第 8 处更正）。
      **行号引用须声明对照基准**（上游 HEAD / 工作区）；本地未提交改动会让整份文档行号漂移。
      **正则类计数：警惕被计对象的命名模式不统一**——同族符号可能有多种拼法，单条正则会系统性漏数。
      **实例**：接口访问器窄正则 `SteamAPI_Steam[A-Za-z]+_v` 漏了 5 个 `_SteamAPI_` 中缀命名
      （`SteamAPI_SteamNetworkingMessages_SteamAPI_v002`），分母从 29 修到 34（第 13 处更正）。
      对策：先抽样看命名全集，双口径（窄/宽）交叉验证；若两口径下**差额集合的属性一致**（如缺口清单相同），结论更稳。

- [ ] **A3. 类型/上限是否查了定义？**
      不能凭代码里的 `as usize` 猜原始类型。
      **实例**：`m_cubParam` 是 `uint32`（上限 4GB），不是 `usize::MAX`。

- [ ] **A4. 竞态类结论：变量是栈上还是跨线程共享？**
      栈上局部变量不存在数据竞争。
      **实例**：误判 `run_callbacks_raw` 的 `callback` 变量有数据竞争，实际是可重入死锁。

- [ ] **A5. 上游是否已修复？（时效性）**
      搜 Issue/PR + 比对当前源码，再断言「仍存在」。
      **实例**：死锁缺陷的主场景早已由 PR #259 修复，我未核查就写了「仍存在」。

- [ ] **A6. 矩阵类结论：对称路径是否逐格测过？**
      「A 方向通 → B 方向也通」不成立；修复只覆盖一半的锁/方向时，反向常是死角。
      **实例**：死锁场景测了「持 callbacks 锁 → 要 call_results 锁」（通），
      没测「持 call_results 锁 → 要 call_results 锁」（死锁，场景 E）。
      列完矩阵后，把**每个持锁上下文 × 每个加锁操作**走一遍才算穷举。

- [ ] **A7. 复现的对照组是否被污染？**
      死锁/竞态测试的对照组必须用**独立实例**——前一个场景死锁线程仍持有锁，
      复用实例会让对照组也报死锁（假阳性）。
      **实例**：场景 E 的对照组 A' 首版复用同一 Mutex 实例，A' 假死锁；换独立实例后正常。

## B. 提「改进方案」前

- [ ] **B1. 仓内是否已有同类问题的正确处理方式？**
      **这是最容易漏的一步。** 只盯着要修的地方，会把仓内优点描述成缺陷。
      **实例 1**：#4 提 `Result` 方案（破坏 23 个公开签名），但 `timeline` 早已用零破坏的
      `disabled` 标记解决同一问题。
      **实例 2**：说「字符串每次分配」，但读侧 14+ 处已是 `CStr::from_ptr` 零拷贝，
      只有写侧有问题。

- [ ] **B2. 区分「检查点」与「受影响公开 API」**
      改的是哪一层？「23 处 null 检查」与「23 个公开方法」破坏面完全不同。
      **实例**：按 23 处检查点估工期，低估了公开签名变更的影响面。

- [ ] **B3. 方案是否需要破坏性 API 变更？**
      需要的话，单独标注并说明版本影响。
      **实例**：39 个 builder 方法 `-> Self` 改 `-> Result<Self,E>` 是破坏性变更，
      不适合作为上游 PR 的独立提交。

- [ ] **B4. 性能类方案是否跑了 benchmark？**
      计数不等于开销。必须实测 + 有效性检验 + 换算到真实场景量级。
      **实例**：「37 处 Arc::clone」实测 8ns/次、占帧预算 0.0005%，性能论据不成立。

## C. 对外发布前（Issue / PR / 评论）

- [ ] **C1. 是否检索过重复报告？**
      `gh issue list --state all --search "<缺陷核心术语>"`。
      **实例**：准备新开死锁 Issue，检索发现 #253 已精确报告同一缺陷。

- [ ] **C2. 需求是否已被维护者确认？**
      CI 全绿 ≠ 该合。CODEOWNERS、审批口径、是否接受重构是维护者的组织决策。
      已有 Issue 时，在**原 Issue 下补新证据**，不另开。

- [ ] **C3. 表述是否把责任归错了对象？**
      **实例**：写「Valve 模板没这问题」易被读成暗示 Valve 设计更好，
      改为说明「这是本 crate 特有的设计约束」。

- [ ] **C4. 未经验证的方案是否标注了？**
      **实例**：`Arc<dyn Fn>` 方案来自自己的设计文档，未在本仓实测，
      补一句 `though I haven't prototyped that against this codebase`。

## D. 文档收尾

- [ ] **D1. 自我更正原文保留，不悄悄改**
      读者需要看到判断是怎么被推翻的，包括错在哪、正确的事实是什么。

- [ ] **D2. 修改处与全文其他引用同步**
      改了一处结论，要搜全部引用点（摘要表、决策、路线图、总结段）一起改。
      **实例**：删掉「可直接作为 PR 上游」时，发现与后文纪律修正直接矛盾。

- [ ] **D3. 编辑时确认没覆盖掉原有内容**
      用 Edit 替换段落时，确认 `old_string` 是完整段落而非其中一段。
      **实例**：替换「73 处」段落时覆盖了相邻的「真实触发场景」四点。
      **实例 2（2026-10-13 再犯同一形态）**：把新写的一节插进 `SuperSteam-Design.md` 时，
      `old_string` 只取了**目标要点的第一行**，结果把「审计中我自己的两把窄尺」这条要点拦腰截断，
      留下以 `折到下一行）；…` 开头的孤儿片段。当场靠 `grep` 该要点的标题行**查无此条**才发现。
      **可复用判据**：对已有文档做插入/替换后，立刻 `grep` 被替换要点的关键标题行是否仍在；
      并数一次文件行数变化是否符合预期（本次 +41，与新增小节体量相称）。
      附带教训：**自查用的启发式尺也会误报**——我用「非列表行紧接缩进行」扫断句，30 条命中里
      `}` / ``` 全是代码块闭合、`3.` 是合法有序列表项，**真断句只有 1 条**；扫全文找异常时
      命中数偏高要先怀疑尺子。

其中 **A2（计数可复算）仍是最高频失误点**——且 #15 是它的**二阶形态**：不是新写的数错，而是
「已经发出去的数从没被整体回算过」。
其中 **A2（计数可复算）是最高频失误点**，拦住 4 处——且第 8 处是「给计数错误本身写了一段辩护」的二阶失误：正则复算之前，没人重新跑过 grep。

这个检验的意义：清单不是事后编的故事，而是从真实错误里反推出来的。
若将来再出现新的自我更正，先检查它该被哪一步拦住——若哪一步都拦不住，说明清单有缺口，需要补步骤。

**第 8 处引出的新增纪律**（并入 A2）：
- 「这个数字没错」类断言本身要**重新跑一遍 grep** 才能写，历史提交也要抽查（`git grep ... HEAD~N`）——数字可能来自已失效的本地改动。
- 行号引用要**声明对照基准**（上游 HEAD / 工作区），本地未提交改动会让整份文档漂移。

**第 13/14 处引出的新增纪律**（并入 A2）——**正则类计数会系统性漏掉两类东西**：
- **命名变体**（#7）：同族符号有多种拼法（`SteamAPI_SteamX_vN` vs `SteamAPI_SteamX_SteamAPI_vN`），单条正则漏数。对策：先看符号全集，双口径交叉。
- **跨行链式调用**（#5）：`.expect()`/`.unwrap()` 被 rustfmt 折到下一行，单行 grep 匹配不到。对策：用跨行扫描或 AST 计数，不信任单行正则。
两者是同一失败模式的两个面：**窄正则只匹配「格式恰好统一」的子集**。计数结论一律双口径（窄 grep + 宽扫描），并公布两者差值的归因。
